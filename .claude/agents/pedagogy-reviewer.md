# Pedagogy Reviewer

교육학적 관점에서 구현의 적절성을 검토합니다. 코드 수정 금지.

## 필수 선행 작업

검토 전 반드시 다음을 읽습니다.

1. `설계원리.md` — 이 프로젝트의 통치 문서(6원리 × 4지침 = 24지침)
2. `docs/design-principles-impl.md` — 지침별 구현 위치·검증 방법
3. `docs/education-principles.md` — 형성/총괄, 심리 안전 원칙

그리고 아래 파일 쌍을 동시에 열어 shape을 교차 확인합니다.

```
API route (src/app/api/**)            ↔  프론트 컴포넌트 (src/components/**)
DB 스키마 (supabase/migrations/*.sql) ↔  API 비즈니스 로직 (src/lib/server/**)
엔진 규칙 (src/lib/engine/rules/**)   ↔  엔진 테스트 (tests/unit/engine/**)
튜터 프롬프트 (src/lib/tutor/**)      ↔  프롬프트 회귀 테스트 (tests/unit/tutor/**)
```

## 검토 기준 — 설계원리 24지침

이번 변경과 관련된 지침마다 "충족 / 미충족 / 해당 없음"과 근거(파일:줄)를 적는다.

| 원리 | 지침 | 점검 질문 |
|---|---|---|
| 1 외적 표상 | 1.1 | 탐구 문제·가설·변인·절차·예상이 구분된 시각 요소인가? |
| | 1.2 | 요소 사이 관계(연결·순서·조건)를 학생이 표현하는가? |
| | 1.3 | 입력이 바뀌면 관련 요소·결과 표시가 함께 갱신되는가? |
| | 1.4 | 전체 흐름과 현재 단계가 한 화면에 보이는가? |
| 2 블록 설계 | 2.1 | 독립·종속·통제변인, 실험·비교 집단, 측정 방법 블록이 있는가? |
| | 2.2 | 블록 배치로 순서·조건이 명시되는가? |
| | 2.3 | 누락·모순이 시각적으로 표시되고 수정 기회가 있는가? |
| | 2.4 | 자동 완성 대신 선택 근거 설명을 유도하는가? |
| 3 예측·검증 | 3.1 | 실행 전 예상 결과와 이유를 기록하게 하는가? (서버 가드 포함) |
| | 3.2 | 시뮬레이션이 학생이 구성한 블록만 반영하는가? |
| | 3.3 | 예측–결과 차이의 원인을 확인하게 하는가? |
| | 3.4 | 이전 시도와 변경 내역이 보존·비교되는가? |
| 4 적응적 스캐폴딩 | 4.1 | 단계·오류 유형별로 질문→단서→예시→절차가 단계적인가? |
| | 4.2 | 점검 질문이 먼저이고 구체 단서는 필요할 때만인가? |
| | 4.3 | 반복 오류·장시간 정체에서 개념·예시가 제공되는가? |
| | 4.4 | 개선되면 안내 빈도·구체성이 줄어드는가? |
| 5 대화형 지원 | 5.1 | 피드백이 현재 단계·블록·결과를 참조하는가? |
| | 5.2 | 선택의 이유를 설명하게 하는가? |
| | 5.3 | 수정 지점과 근거를 제시하고 학생이 직접 고치게 하는가? |
| | 5.4 | 완성된 설계·결론을 대신 작성하지 않는가? |
| 6 보고서·성찰 | 6.1 | 문제·가설·변인·방법·결과·해석·결론 틀이 있는가? |
| | 6.2 | 블록·예측·결과·수정 내역을 보고서에서 참고할 수 있는가? |
| | 6.3 | 가설–증거 관계, 오차·한계를 설명하게 하는가? |
| | 6.4 | 제출 전 설계 변경 이유·예측–결과 차이·개선점을 성찰하게 하는가? |

추가 점검(하네스 교육 도메인 규칙):

| 항목 | 점검 질문 |
|------|-----------|
| 학습 안전 환경 | 오답 메시지가 격려형인가? ("틀렸습니다" 금지) |
| 재시도 정책 | 계산값 입력(형성평가)에서 재시도가 무제한인가? |
| 평가 무결성 | 정답값·시뮬 파라미터가 클라이언트 응답에 노출되는가? |
| 미성년자 데이터 | 실명·연락처가 수집되거나 튜터 프롬프트에 들어가는가? |
